# Solar Panels

A solar-powered mobile network base station site can contain one or more solar panels. The API stores each panel as a separate record and links it to the site where it is installed.

This relationship allows the API to manage panel information without duplicating site data.

## Relationship Between Sites and Solar Panels

The API models a **one-to-many relationship** between sites and solar panels:

- one site can have multiple solar panels
- each solar panel belongs to one site

For example, the `Pretoria Central` site might contain the following panels:

```text
Pretoria Central
├── SP-101
├── SP-102
└── SP-103
```

The `site_id` field in each solar-panel record links the panel to its parent site.

In the database, `site_id` is a foreign key that references `sites.id`.

This relationship keeps site and panel records separate while letting the application determine which panels belong to a particular site.

## Solar Panel Identification

The API uses three identifiers when working with a solar panel:

| Field | Purpose | Update allowed |
|---|---|---:|
| `id` | Identifies the solar-panel database record | No |
| `site_id` | Identifies the site where the panel is installed | No |
| `panel_code` | Identifies the panel within the site | No |

The API generates the panel `id` when it creates the record.

The site comes from the request path. For example:

```http
POST /sites/1/panels
```

In this request, `1` identifies the parent site. Clients do not provide `site_id` in the request body.

## Panel Codes

A panel code identifies a solar panel within a site.

For example:

```text
SP-101
```

A site cannot contain two panels with the same `panel_code`.

However, the same panel code can exist at different sites.

For example:

```text
Site 1 → SP-101
Site 2 → SP-101
```

This design reflects the database constraint on the `site_id` and `panel_code` combination.

If a client tries to create a duplicate panel code at the same site, the API returns a `409 Conflict` response.

## Solar Panel Fields

| Field | Type | Description |
|---|---|---|
| `id` | integer | Unique identifier generated by the API |
| `site_id` | integer | Identifier of the site where the panel is installed |
| `panel_code` | string | Operational identifier for the panel |
| `capacity_watts` | number | Rated maximum power output in watts |
| `status` | string | Current operating state of the panel |
| `created_at` | date-time | Date and time when the record was created |
| `updated_at` | date-time | Date and time when the record was last updated |

The API generates `id`, `site_id`, `created_at`, and `updated_at`.

Clients provide `panel_code` and `capacity_watts` when creating a panel. They can also provide `status`. If they omit `status`, the API assigns `operational`.

## Panel Capacity

The `capacity_watts` field stores the panel's rated maximum output.

For example:

```json
{
  "panel_code": "SP-101",
  "capacity_watts": 550.0
}
```

The value must be greater than zero.

The API stores panel capacity separately from actual power readings. Capacity describes what the panel is rated to produce, while a future power-reading resource will record measured output over time.

## Panel Status

A solar panel can have one of the following status values:

| Status | Meaning |
|---|---|
| `operational` | The panel is available for normal operation |
| `maintenance` | The panel is undergoing maintenance |
| `offline` | The panel is not operating |

If a client does not provide a status when creating a panel, the API assigns `operational`.

## Updating a Solar Panel

The current panel update operation can change:

- `capacity_watts`
- `status`

The operation does not change `panel_code` or `site_id`.

Keeping these values unchanged preserves the panel's identity and its relationship with the parent site.

## Deleting Sites That Contain Panels

The API does not allow a client to delete a site while solar panels are still associated with it.

If a client attempts to delete such a site, the API returns a `409 Conflict` response.

The client must delete the site's solar-panel records before deleting the site itself.

This rule prevents the API from leaving panel records without a valid parent site.
